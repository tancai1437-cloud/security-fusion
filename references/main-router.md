**第一层：主路由；第二层：专项路由。**

三个层级由同一Agent执行。第一层维持任务目标、计划和进度；第二层提供当前检查的专业方法；第三层选择工具/MCP和具体调用。能力ID是第三层的匹配字段，不新增第四个主层级。

**意图优先。**

- 完整渗透 → pentest；SRC/众测 → src；逆向 → reverse；源码审计 → audit；约定红队路径/检测场景 → redteam；AI应用边界 → ai-assessment。
- “只分析这个函数”“只核对一个问题” → 相应专项的有限任务，报告规模与任务匹配。
- “设计Skill/写方案/调研项目” → 只读产物路径，不启动目标测试。
- 完整任务中出现JS/APK/源码材料只增加专项候选，mission_id保持不变。只有用户改变主要目标才切换主流程。

**每轮工作。**

1. 新案件按 [快速执行](first-action.md) 用 start 登记首项并执行已有本地工具；已有案件、压缩后或切换案件时运行 fusion.py resume 获取当前目标、范围、约束和检查；连续执行沿用回执，仅在阶段切换或状态不明时更新快照。不要每轮加载全部历史。
2. 选择依赖已满足的工作项；先处理能够解除后续阻塞或显著补充覆盖的项。
3. 读取当前专项，并传递case_root、workitem_id、target_refs、identity_refs、scope_ref、evidence_refs、完成条件、预算和return_to。
4. 专项请求一个或若干执行能力，执行路由解析MCP选择和参数；实际工具调用由当前Agent完成。
5. 用运行协议保存每次调用、证据和结果。阴性、被否定假设、失败原因及简明决策也写 note；事实、候选问题、确认问题分别维护。
6. 新线索满足触发条件时修订计划。先 query --kind checks/notes --target 核对同目标历史；plan 按结构化指纹确定同一检查，不依赖模型“记住做过”。语义相似但字段不同仍需 Agent 判断；采样和覆盖边界保留。
7. 继续下一工作项。没有可执行项时核对完成、缺输入、工具受阻或预算耗尽，生成真实状态的交付。

模板中的core是默认候选检查，不是无条件必跑。conditional只有在目标具备该面且范围允许时加入。报告与复核可在部分完成时运行；不能等待某个长期阻塞项而丢失所有交付。

**选择下一项的依据。** 当前面还有可执行检查时，优先消除其关键不确定性；新地址或功能先带来源落盘，范围与绑定核对后再加入。当前面完成、缺少前提或预算要求切换时处理下一面，不因为资产搜索容易产生数量就反复扩面。每次切换留清楚已测边界、未测/受阻项和恢复条件；全部适用项完成后交付，不自动进入无限随机重探。

只有当前响应/代码出现对应业务特征时才追加专项。选型不明确时按 [特征路由](field-methods.md#features) 查相关行；成功或失败后回到本站实际清单，不把某一方法当全部覆盖。类型优先级可以按项目要求调整，不能把来源作者的“不测某类”变成全局排除。

**第二层专项组合。**

完整Web/API任务通常从fusion-recon建立基线，再按事实安排fusion-web、fusion-api、fusion-business；前端依赖交fusion-js，有源码交fusion-code。样本任务先按移动框架/二进制类型安排fusion-mobile或fusion-binary。云、网络身份和AI专项按环境事实加入。

每个专项只向主控返回结果与后续条件；不调用另一个独立Agent，不反复问用户选择下一菜单。专项可以建议另一个专项，但由主控统一去重和安排。

**状态与停止。**

账本检查：pending / running / review / done / failed / blocked / unknown；读时可能派生 stale / evidence_invalid / dependency_changed。适用性和未纳入计划的检查面另存专项覆盖说明。业务完成与调用返回分别记录；不适用项保存依据，不能伪装成 done。

任务：completed / partial / failed / cancelled。所有适用项满足完成证据且报告检查通过，才为completed。单个候选被否定后，其他检查仍继续。用户终止、预算耗尽或无法继续时保存恢复信息并交付对应状态。

运行辅助程序 report 的 completed 仅限已登记计划；主控还必须核对适用面和最终技术报告。命令与恢复步骤见 [运行协议](runtime.md)。
