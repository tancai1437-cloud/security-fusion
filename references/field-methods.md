# 根据现场证据推进检查

用于 Web/SRC 任务已经取得第一份响应、流量或代码证据之后。只读当前专项对应的小节；不把本页或整套方法库变成起手必读。这里是第二层的方法选择，工具仍走现有第三层能力路由。方法线索不等于目标存在漏洞，也不增加原有任务范围。

## features

不知道下一项检查什么时，用实际观察匹配一行；只打开命中的专项。保留观察来源，缺少相应业务功能时不因为表里有一行而安排测试。

| 实际观察 | 专项与执行能力 | 这一步要弄清楚什么 |
|---|---|---|
| 页面脚本、请求发起位置与文档不一致 | fusion-js：js.source / http.history | 实际路径、方法、参数、身份传递来自哪里；静态路径是否真的被调用 |
| 登录、角色、租户或带对象标识的接口 | fusion-api：http.history / http.request | 测试身份是否生效、对象属于谁、该动作按业务规则应允许还是拒绝 |
| 上传、下载、分享或文件转换 | fusion-web：http.request / browser.observe | 文件归属、读取/修改边界与实际处理结果；自己的文件成功不能证明越权 |
| 搜索、筛选、模板或富文本输入 | fusion-web：http.request / browser.observe | 输入进入哪种处理/输出位置；正常对照与异常是否稳定、是否有真实边界影响 |
| URL 预览、导入、回调或外部集成 | fusion-web：http.request / http.history | 请求来自浏览器还是服务端，来源限制和可控测试回调能证明什么 |
| 订单、审批、额度或多阶段提交 | fusion-business：http.request / code.inspect | 哪条业务不变量应保持，服务端前后状态是否真正改变 |
| GraphQL、WebSocket 或不同网关路径 | fusion-api：http.history / http.request | 消息/操作自己的身份边界是否有效；握手或入口成功不代表每项操作获准 |
| 缓存、跨源读取或浏览器权限策略线索 | fusion-web：http.history / browser.observe | 在现实前提下是否影响其他身份/上下文；单个头部或架构名称不足以确认 |
| AI 应用出现工具、文件、检索或外部动作 | fusion-ai：ai.boundary / http.history | 是否有实际工具调用和越界结果；模型文本自称成功不作执行证据 |

## recon

**先消化已有入口。** 当前业务面还有可执行、能缩小关键不确定性的检查时，优先继续它。新发现的地址、对象标识、文档或业务功能，带来源记入当前案件的 fact/decision；确认范围、目标绑定和依赖后再 plan。只有现有材料不足、当前面已完成或确实受阻时才扩大采集。搜索命中数、端口数和目录数分别说明，不当作已测数量。

**按业务差异去重。** 资产记录可归一化主机/端口；检查仍区分路径、方法、语义参数、身份、目标版本和测试条件。路径与方法等放入既有 inputs，不能因同一主机已测过就丢掉新的业务接口，也不能换个 key 重跑同一检查。发现未绑定的新目标先隔离登记，不通过修改旧绑定扩大范围。

**采样有边界。** 相似页面可参考构建指纹、API 前缀、身份流程和响应行为选择代表，节省重复检查；仅标题相同不够。未逐项验证的实例标为采样覆盖或未测，不能继承代表的 done。新路径、不同身份控制或业务行为出现时，重新判断适用性。

## web

**从业务入口建立差分。** 先确认正常请求、资源不存在、身份缺失时分别返回什么。关注响应含义、对象归属和实际状态，不只比较状态码、长度或某个字符串。模板命中仍交 validate，模板数量不等于覆盖。

**区分登录壳与业务行为。** 任意路径都返回同一登录 HTML 时，记录统一兜底现象，改用已观察到的业务请求或已知前端线索定位真实入口。已定位业务 API 且它们被同一已验证的身份前置条件阻挡时，停止对该拒绝响应重复做下游输入检查，记录缺少什么身份/条件，继续独立面。不能据此认定整个站点安全；登录、找回、身份交换等仍按实际适用性单独判断。结构化空列表也不等同于登录拒绝。

**有依据才重试。** 偶发超时、500 或一次延迟先与正常对照核对。没有稳定差异且前提未改变时，记录本条件下的阴性/不确定结果，不为得到某个预期现象不断重发。具体重试和未知副作用处理沿用执行协议。

## api

**从一个对象展开权限关系。** 记录测试身份、角色/租户、对象归属和实际动作；围绕同一受控对象比较正常允许与预期拒绝。列表、详情、导出、分享、修改等按实际出现的动作加入，不假设它们共用鉴权，也不凭接口名编造不存在的动作。

**认证与业务校验分开。** 先确认请求格式有效、身份确实生效，再判断权限。输入校验错误、统一成功包装、过期会话、自有对象返回，都不能单独证明跨身份访问。权限不足只阻塞需要该身份的检查，不抹掉已完成的匿名基线。

## js

**提取足以发起正确请求的上下文。** 除路径外，保留请求方法、参数构造、base URL、身份传递方式、响应解析和代码位置；敏感值仅保存安全引用。抓包与实际调用链优先验证静态推断，不把字符串里的所有路径都当活接口。

**材料缺失时换证据来源。** JS 无法获取时使用已有流量、HTML 内联内容、用户提供的接口文档和响应链接，注明覆盖损失。纯 API 任务不等待前端工具。异步脚本或 source map 仅在能回答当前问题且在范围内时取用，不默认下载所有脚本。

## business

**围绕已发现问题补足解释。** 当前对象出现可复现异常时，先核对相关前置条件、服务端状态和影响边界，再决定是否转向新对象；不要在只有一个表面现象时急于汇总报告。进一步检查必须回答明确的新问题，并沿用任务对写入、支付及其他副作用的限制。

**影响由证据决定。** 可见界面按钮、角色名称或接受了请求，分别只能说明相应事实。报告区分已观察的变化、从可信实现推导的影响和未验证可能性；不为提高等级强行扩大操作，也不因结果等级不高而丢弃有效结论。

## ai

**跟踪工具边界。** 将用户输入、检索内容、模型输出、实际工具请求及工具结果分开。工具名称可见仅触发权限和上下文核对；文本声称访问了文件、执行了命令或完成了外部动作，必须有对应调用及结果支持。缺少工具执行能力时保留该限制，不将它作为整个应用安全的结论。

## validate

**每个候选保留四个要点。** 触发事实、适用前提、足以成立的结果、可能推翻它的替代解释。说明“相对正常对照，多发生了什么，为什么不符合业务预期”，并指向原始证据。单次失败只否定本次条件下的主张，不能自动宣布整类方法失效。

**覆盖与漏洞结论分别写。** 检查 done 只说明完成条件已满足；阴性检查也可 done。不能把未登录测试扩写成已覆盖登录后功能，不能用代表样本的结果替所有实例定论。缺身份/材料为受阻，真实功能不存在才可说明不适用，因优先级/预算未做的写未测。

## learning

阶段结束使用既有 memory-add / memory-review，不额外创建学习代理或自动改写正式 Skill。选择经验前判断：

1. 换一个具有相同业务形态的目标，适用条件和方法是否仍然有意义？仅有这次的地址、字段或偶然故障，留在案件记录。
2. 相比已有方法，新增的是容易遗漏的前提、判定方法、证据要求还是反例？只有新目标名称或再次成功，不新增经验卡。
3. 新结论是否有已复核来源，且能说明何时不能套用？证据不够则保留假设，不晋级。

已有同类经验时只提炼差异；程序仍以 supersedes 创建可审核的新版本，保留旧版审计，不原地改掉历史。中低风险结果、阴性结论和假阳性识别只要可复用且有证据也能沉淀，不按漏洞等级独断筛选。单站超时、401 或无发现不构成通用反例，条件必须写清。
