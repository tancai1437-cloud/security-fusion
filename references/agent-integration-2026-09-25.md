## 恢复与上下文

候选两次实际调用 DSH compaction，分别压缩约 30,494 与 39,926 个估算 token 的旧记录，摘要分别为 9,561 与 737 字符。第二份摘要很短；宿主仍从磁盘恢复了案件状态，不需要从该摘要猜路径。

宿主恢复来源消息在第二、第三轮首步分别出现，大小为 6,109 与 1,989 字符（包含宿主路径和提示；其中 CLI 恢复包上限为 6,000 字符）。连续执行不逐步重灌全包，工具故障状态改变也会触发刷新。此次三轮共 9 次恢复消息。

供应商上报的普通模型步骤用量，前两轮基线为 3,783,508 totalTokens，候选为 2,000,091；其中大多数是 cacheReadTokens。未包含压缩调用、失败实验及接口探测，不能用此数字直接宣称费用下降。未缓存 inputTokens 分别为 105,312 和 97,382，outputTokens 分别为 52,980 和 47,797。

## 真实失败与修正

1. 本机 `web_fetch` 缺少 `undici`，真实调用失败；`web_search` 可用，模型通过已有 Python/curl 取得正文。此插件不修复 DSH 本体依赖，没有把失败 fetch 当作成功。
2. 初次测试给压缩摘要设了 2,048 token 上限，Qwen 输出被截断，DSH 正确拒绝使用。恢复到该 DSH 的默认 8,192 上限后，用原持久会话继续，压缩成功。没有将截断摘要作为合格恢复证据。
3. 第一版桥接在 DSH 中丢失子进程 stdout，而独立 Node 测试通过。修正为 `execFile` 回调接口后，真实宿主工具预检和完整模型测试均成功；补了宿主包装 `execFile` 的回归测试。
4. 模型会猜错参数或路径。实际出现 `note --kind summary` 和凭记忆编造证据目录。末次联调后补充合法笔记类型提示、全部检查结束后的 `query → resume --check → evidence[].path` 定位提示，并完成定向回归。未将这些提示声明为绝对遵循保证。

## 接入和限制

使用 [DSH 宿主适配说明](host-adapter.md)。普通 `skills add` 只下载文件，接入插件后才有原生 `fusion` 和自动恢复。

- 会话隔离验证覆盖宿主实际 session ID 对应的账本、恢复状态与案例路径；任意宿主命令或项目根目录文件写入不受本插件隔离，不是完整沙箱。
- 没有进入用户的 Kali，也没有验证其自定义 `tool-index.md` / `eng/tools/` 规则。
- 没有验证 Pi、OpenCode 的宿主 hook 或全部 13 个专项；没有完成真实第三方 MCP 服务的本轮联调。
- 本例显示了可用性和一次执行效率改善，不能推出所有长任务都不会跑偏，也不能推出 Qwen 是所有已配置模型中最强的。
