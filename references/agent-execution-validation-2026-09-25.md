# DSH 执行约束：实测与边界（2026-09-25）

本轮针对“已加载 Skill，随后自由发挥”实施宿主约束，并用真实模型验证。**Web 任务已改善并交付；原条件下的 JS 任务仍未通过，不能宣称彻底解决所有模型的执行问题。**

## 条件与计数

- Windows / PowerShell，真实 DSH 0.1.2-rc.1、dsh-base；独立 profile 和项目，顺序运行，无子代理。
- 模型为用户已配置服务的 Qwen3.8-27B-Uncensored；未独立核验服务端权重，不声称本 Windows 主机部署了这些权重。
- 旧版为 `7a9bc4c` 的纯 Skill；新版增加 DSH 宿主组件。比较的是接入方案变化，不是两份文字提示的同条件排名。
- 每次最多 120 次根工具调用 / 19 分钟。阶段一结束后做真实压缩（上限 8192、retainTokens=256、重试 0），仅给通用“继续”指令进入阶段二。
- 根工具调用、宿主内实际子调用、MCP 服务回执分别计数；被拒绝调用不算实际执行。原始推理、凭据与服务地址不公开。

### Web

受控服务只有 `/alpha` 在范围，回显 XFF，`protected_access` 始终为 false。新版读取了 fusion-web 与代理信任方法，完成联网搜索与官方资料读取、真实 HTTP/MCP 调用、压缩、继续、专项产物和报告。两阶段均正常结束，总耗时 671.9 秒。

宿主捕获 20 次实际工具执行，拦截 3 次裸调用；全部 6 次目标请求位于 `/alpha`。报告正确区分“输入可影响显示”与“权限决策受影响”，没有把计划中的请求写成已执行。

仍有两个限制：

1. 本来需一次基线和随后三组对照，实际产生 6 次请求：MCP 做过单地址、多地址链后，又用脚本跑完整三组。多出两次跨工具重复。已修改方法为优先复用、只补缺组；参数指纹不能识别任意 shell 改写后的语义重复。
2. 共同宿主故障 `web_fetch` 缺少 undici，由模型改用 curl。账本还保留三项已被替代的失败尝试，因此如实按 partial 提交。报告中的核心观察有证据，不等于环境和全过程无故障。

### JS

样本为自建离线签名程序，要求独立 Python 标准库复现。新版在第一阶段完成源码/哈希、真实样本执行、MCP 与联网查证，20 次根调用后 checkpoint。压缩成功，覆盖 31,754 tokens；第二阶段磁盘恢复消息已进入上下文。

随后模型单次耗尽 32,768 输出 tokens，没有工具调用或 replica.py，DSH 以 `max-tokens` 结束。**这是失败，没有可评分程序，不能记为通过或伪造 0/20 的程序正确率。** 当前入口不能强迫一个完全不发出调用的模型开始执行。

### 单独的受限续测

先尝试已配置的 GLM；完整上下文请求返回 QUOTA，未执行工具。此前小请求连接成功不能代表额度足够支持完整任务。

再用同一 Qwen 会话续跑，将输出上限设为 8192，请求关闭 thinking，并补充“先落盘最小程序，再逐项实测修正”的指引；未提供答案或盲测输入，也未修改被测程序。这些条件已改变，因此单列：新增 8 次根工具调用，其中 7 次 fusion；最终写出 replica.py，但存在 `invalid hexadecimal literal` 语法错误，不能启动，未进入输出盲测。随后仍以 max-tokens 结束。不能据此声称服务实际完全关闭了 thinking，也不能把这次写文件算作复现成功。

最终宿主记录 `interrupted_without_delivery` 和真实结束原因，closure 为空。新的宿主约束已在真实额度失败和输出上限场景中留下中断状态。模型完全停止发出调用时不会无限补发请求，保留案件供后续恢复。

## 工程验收与后续修正

- 最终自动化测试 136 项：133 通过，3 项因宿主条件跳过；其中 DSH 桥接测试实际运行 10 个 Node 用例。验证真实回环 HTTP、重启查重、未知调用不重发、跨会话隔离、伪造/篡改回执拒绝、专项产物缺失、安装升级/卸载与历史证据有效期。目录非空检查已通过；本 Windows 主机不可用的越界 symlink 创建测试跳过，不能冒充已测。
- `finish` 现在直接给出未复核调用 ID，避免只报数量导致反复查账；专项产物缺失只能明确 partial。模型输出上限和取消等强制结束另记录实际原因，不依赖正常结束 hook。
- 修复专项导出目录被误按普通文件检查的问题：目录必须含本案内非空文件，越界链接拒绝，目录过大时明确标为未验收；文件/目录存在仍不证明内容正确。
- Web 实际产物另经最终交付检查代码复验：报告哈希一致，专项缺口为空，状态仍是 partial。该检查未发任何新目标请求，不冒充另一轮模型实测。
- JS 正式运行通过本包安装器加载宿主组件。最终的小幅错误提示/结束检查增强有回归测试；不把开发过程中先前快照的结果说成最终字节完全一致的整轮测试。
- `sentrux gate` 对原始基线检查无结构退化。仓库没有 `.sentrux/rules.toml`，因此不声称 `sentrux check` 的架构规则验收通过。

## 能约束什么

已激活执行任务中的 shell、搜索、文件操作和 MCP 应经过 `fusion.execute`；宿主校验声明的专项/能力组合，沿原生权限流程调用真实工具，自动登记回执。压缩后恢复磁盘状态；缺记录/缺交付时拒绝完整结束或有限纠正。失败、暂停和部分交付均有明确状态。

这不能证明模型选对全部测试面、能力标签一定匹配工具实际用途、代码和报告结论一定正确，也不是限制任意 shell 网络访问的沙箱。报告引用真实调用 ID 只证明该调用存在，不能代替逐条结论核验。仅安装 Skill 文本没有这些宿主能力。

本轮未验证 Kali、其他 DSH 版本、Pi/OpenCode、生产逆向 MCP 或全部 13 个专项。安装与回退见 [宿主组件](host-adapter.md)。
