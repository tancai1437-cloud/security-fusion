# 固定模型的可靠性改进循环

本轮完成一个基线和七轮改进复测，共十次目标试验。修复了已经复现的参数丢失、路由条件继承、回执引用和中断落盘问题；最后两轮主任务均在真实压缩后继续执行并完成原生阶段交付。两个短时第二会话仍超时，研究结论也仍需要人工复核。本记录不能作为“全自动渗透通过”或优于其他 Skill 的成绩。

完整脱敏计数与每轮源包哈希见 [指标 JSON](../benchmarks/reliability-20261006.json)。原始回执、请求、身份材料和报告保存在私有测试目录，不随安装包发布。

## 验收约定（运行前固定）

1. 已绑定 HTTP GET/HEAD 可使用当前路由和精确参数完成检查；参数改变不能继承旧试验条件，相同有效观察可恢复复用。写操作、未知工具与跨工具语义复用仍要求明确条件。
2. 复核当前结果无需抄写长 ID；旧结果只能按本会话唯一前缀/完整 ID 定位。错误/歧义引用在新执行前拒绝，并给出可恢复信息；不能模糊匹配或串案。
3. 原生压缩后从既有证据继续，实际请求与回执可对应，产物哈希完整。不能只凭“压缩成功”推断任务恢复正确。
4. 公开版本/客户端配置、前端守卫和状态码不能单独支持“已确认权限缺陷”。阶段报告区分证据、候选、确认及未完成项；调用统计与观察器一致。
5. 修复通过确定性回归，并至少进行两轮新的同模型实测；保留失败轮与源包哈希。有限样本只证明本次验收范围，不宣称全部模型/专项可靠。

## 环境与计数方法

- 模型固定为 `opencode-free/space-bunny-free`，来自 [OpenCode 免费模型服务](https://opencode.ai/docs/zen/)，未切换到收费模型。本轮没有以 Qwen 27B 执行，不能据此评价 Qwen。
- Windows 本地 DSH `0.1.2-rc.1`；每轮冻结独立 Skill 副本、profile、状态目录和容器。主任务显式要求使用 Skill，未评测自然唤醒率。
- Juice Shop 镜像固定为 `bkimminich/juice-shop@sha256:8739101ade29358abb5469ee66ae78e582c97ed0a5543a4ad102e5fa5193526b`。实际目标请求全部由 DSH 经真实 stdio HTTP MCP 发出；评测器只部署、被动记录和离线核验。
- 基线至第 5 轮：A 执行 90 秒，实际原生压缩，再执行 90 秒。第 6、7 轮：A 两阶段各最多 180 秒，中间实际压缩；随后在同一项目工作目录开启新会话 B，针对另一新容器执行最多 120 秒。
- 压缩调用 DSH 原生 `compactNow`；取消后回合仍开放时使用原生 `compactRegion`。保留实际返回事件，没有伪造回合结束或只替换提示词。
- HTTP 次数来自被动流量记录。工具错误是宿主观察到的参数拒绝、引用错误或绕路拦截等，不等于 HTTP 500 次数。文件写入与路由包装器不混入 HTTP 计数。

后续轮次根据已观察问题修改了实现，预算也有调整，因此这是工程改进记录，不是随机、盲测的性能排行榜。[四组对照排程](../benchmarks/README.md)另行管理，尚未执行完毕。

## 从失败中修复了什么

| 已复现问题 | 最终实现 | 保留的约束 |
|---|---|---|
| DSH 接受外层字段，适配器却只读取 request，导致 arguments 被静默丢掉 | 已知字段先归一化，再交给原 schema；外层与 request 不重叠时可组合 | 冲突字段、未知字段、混用 input_json 被明确拒绝；不改写请求内容 |
| 当前路由已存在，却因缺 work 错报缺少工具 | 先找当前兼容路由，再验证本次调用条件 | 只有维护者明确绑定的同源 GET/HEAD 可按精确调用去重；其余操作需 work |
| 变更请求沿用了先前 work | 新参数清除旧 work 默认值 | 身份、版本和参数继续参与复用判定；不猜跨工具语义 |
| 压缩后频繁抄错长回执 ID | 复核默认上一实际结果，支持本会话唯一短前缀；节点与最终评估同样支持短前缀 | 错误或歧义引用在调用前拒绝，不模糊匹配、不从其他案件补答案 |
| 强制取消时没有结束 hook，磁盘上缺少易读续接点 | 每次回执持久化和复核后原子更新 `report/runtime-checkpoint.md` | 检查点标明最近状态、原始账本与下一步，不冒充完整报告 |
| 交付摘要被 1,200 字符上限反复拒绝 | finish/deliver 摘要允许至 6,000 字符；缺省摘要只说明阶段导出 | 长摘要完整落盘，恢复块放读取指针；普通复核/检查点仍有短预算 |
| 公开配置和错误响应被夸大为漏洞 | API/Web/报告方法卡强化身份对照、实际影响和阴性结果限定 | 不将此靶场路径、答案或具体输入加入方法卡；程序不替模型证明语义 |

## 恢复、隔离与上下文

最后两轮 A 在压缩后有新的真实请求并引用先前证据继续调查，随后交付阶段结果；这证明本轮短周期恢复链路已走通。路由复用、进程对象重建、未知状态不重放、不同身份参数和跨会话回执拒绝另有确定性回归。没有进行真实 DSH 进程重启或数小时任务压力测试，不能把单测替代这些结论。

第 6、7 轮的 A/B 使用同一项目工作目录，但真实 session owner、案件目标和账本不同。离线逐项核对 47 份调用回执及 141 份产物：共享产物 ID 为零，回执 owner/target 均归属本案，A/B 的实际 MCP 叶子调用分别只进入各自目标。没有实现进程级私有验收器隔离，这只是本轮会话与路由隔离证据。

八轮最大恢复块为 **7,991 字符**；第 7 轮 A 最大为 7,510，B 为 7,952。上限约束的是单条宿主恢复消息，不是完整对话，也不是 token 数。历史回执、长报告与完整方法按需读取；长交付摘要不再挤掉恢复时的关键指针。

提供商回传的全部十次试验 `totalTokens` 合计 **4,828,443**，包含其原始缓存计数口径，未加算未回传的压缩用量，也没有再把缓存字段重复叠加。因此不能宣称整体低消耗，更不能据此推算收费金额。第 6 → 7 轮 A 的压缩后执行时间为 178.652 → 112.838 秒，回传总量为 1,212,382 → 775,067；任务轨迹不同、样本仅各一次，只记录变化，不声称已证明固定提速或节省比例。

## 研究结论的人工复核

基线和第 2 轮将公开配置推导为权限问题，不能接受。针对所用版本离线核对 [配置路由源码](https://github.com/juice-shop/juice-shop/blob/v20.2.0/routes/appConfiguration.ts) 与 [路由注册](https://github.com/juice-shop/juice-shop/blob/v20.2.0/server.ts)：公开接口的存在本身不足以证明越权，需要实际权限契约和受保护资源对照。

第 6 轮有错误凭据与另一测试输入的服务端结果对照、后续身份核验、匿名/普通账户/他人对象对照。离线复核只按这些实际响应确认所观察现象；返回 admin 身份不自动证明已成功执行管理员操作。原始身份令牌不公开。

第 7 轮报告区分了确认、候选与未完成项，明确写入成功不证明 XSS，缺少读回/渲染时列为未验证。其两个权限发现涉及对象和功能/角色边界，在本次评估中仍归为访问控制这一大类，不宣传为两个完全独立的漏洞大类突破。若干阴性输入只能说明本次未复现，不能证明相关端点没有其他问题。

第 7 轮 A 仍有四次实际回执 ID 引用错误，被宿主拒绝后以 partial 交付并保留一个待复核项。B 的三次错误分别为直接读取 MCP 产物被拦截、request schema 不匹配、把 content-type 放错字段。不能把这些拦截当作“零错误”或完全遵循，也不能为了降低错误数取消验收。
